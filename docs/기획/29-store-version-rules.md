# 앱 버전 · 빌드 번호 운영 규칙 (#29)

작성일: 2026-11-02

## 결정: 스토어 첫 제출은 1.0

리포 태그 `v1.0`~`v1.7`은 **개발 마일스톤**이다. 스토어에 처음 올리는 앱이 1.7로 시작하면 사용자에게 어색하므로,
스토어 버전은 `1.0`부터 새로 센다. 태그와 스토어 버전이 어긋나는 것은 아래처럼 네임스페이스를 나눠 해결한다.

| 구분 | 형식 | 예 | 뜻 |
|---|---|---|---|
| 개발 마일스톤 태그 | `vX.Y` | `v1.7` | 지금까지의 기능 묶음. **더 만들지 않는다** |
| 스토어 릴리즈 태그 | `store/X.Y[.Z]` | `store/1.0` | App Store에 제출한 커밋 |

`v1.7` 이후의 릴리즈는 `store/` 태그만 붙인다. Releases 페이지도 `store/` 태그로 만든다.

## 버전 번호 (`MARKETING_VERSION`)

- 앱·테스트 타겟 모두 `1.0`으로 맞췄다 (앱 타겟만 `1.0.0`이던 것을 통일).
- 기능 추가 → 두 번째 자리(`1.1`), 버그 수정만 → 세 번째 자리(`1.0.1`).
- 올리는 시점: 스토어 제출 PR에서 올린다. 개발 중에는 다음에 낼 버전 그대로 둔다.

## 빌드 번호 (`CURRENT_PROJECT_VERSION`)

- **App Store Connect에 업로드할 때마다 +1.** TestFlight 업로드도 포함한다. 같은 빌드 번호는 다시 올릴 수 없다.
- 버전이 바뀌어도 0으로 되돌리지 않고 계속 올린다 (`1.0 (3)` → `1.1 (4)`). 업로드 이력을 숫자 하나로 따라갈 수 있다.
- 앱·테스트 타겟을 같이 올린다.

## 앱 안의 표시

설정 화면 맨 아래 "버전" 줄이 `CFBundleShortVersionString (CFBundleVersion)`, 예 `1.0 (1)`을 보여준다
(`SettingsView.appVersion`). 문의가 들어왔을 때 어느 빌드인지 바로 확인하는 용도다.

## 제출 체크리스트 (버전 부분만)

- [ ] `MARKETING_VERSION`이 이번에 낼 버전인지
- [ ] `CURRENT_PROJECT_VERSION`을 직전 업로드보다 1 올렸는지
- [ ] 제출한 커밋에 `store/<버전>` 태그
