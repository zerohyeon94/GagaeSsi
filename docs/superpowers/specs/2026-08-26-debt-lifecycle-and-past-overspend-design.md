## 1. 배경 / 문제

Brain Dump 후속 검토(2026-08-26)에서 확인된 세 가지:

**(A) 과거 날짜 초과가 상환 관리에 들어오지 않는다.**
여행 등으로 며칠 뒤에 소비를 소급 입력하면, 이월 체인은 재계산되지만(2189500)
부채 전환은 일어나지 않는다. 세 경로 모두 막혀 있다:

- `reconciledDebt`: 활성 부채가 없으면 `nil` — 새 부채를 만들지 않는다
- `reconcileDebtTransfer`: `guard previous > 0` — 그날 전환 이력이 없으면 손대지 않는다
- `convertExistingDeficitToDebt`: 오늘의 음수 이월을 **어제** 소비 기준으로만 역산 —
  초과가 며칠 전이면 전환액이 0이 된다

결과: 과거 초과는 음수 이월로만 남아 매일 예산을 갉아먹고, 상환 계획·진행률·
"초과한 날" 관리에서 빠진다. 사용자는 "왜 예산이 계속 적지?"만 보게 된다.

**(B) 부채의 "여정"이 보이지 않는다.**
`SpendingDebt.startedAt`·`completedAt`과 `DebtRepaymentEntry` 원장(날짜·금액·출처)이
전부 쌓이고 있는데, 화면은 남은 금액과 진행바만 보여준다. 언제 시작해서 어떻게
갚아왔고 언제 끝나는지가 없다.

**(C) 여행 같은 큰 지출은 "빚 갚기" 톤이 맞지 않는다.**
갑작스러운 여행 소비도 지금은 초과 → 부채 → 나눠 갚기로만 흘러간다. 동작은 하지만
의도한 큰 지출을 과소비 페널티와 같은 틀에 넣는 것이라, 몇 주간 하루 예산이
쪼그라드는 경험만 남는다.

## 2. 설계 원칙: 부채를 기간이 아니라 수명주기로 다룬다

현재 `reconciledDebt`는 "시작 전날 ~ 어제"라는 **기간**을 스캔해 초과를 합산한다.
과거 날짜 전환이 들어오면 이 방식은 위험하다 — 부채 시작일을 과거로 잡는 순간
그 사이의 무관한 초과일까지 소급해 빨아들인다(이중 계상).

이 설계의 축은 하나다: **부채의 구성 근거를 "실제로 부채로 옮긴 날들"의 집합으로
바꾼다.** 전환할 때마다 남기는 `debtTransfer` 상쇄 크레딧이 이미 멱등 장부 역할을
하고 있으므로(280b8d4에서 정리), 이 크레딧이 붙은 날이 곧 부채의 구성원이다.

이렇게 하면:
- 재계산(1절)과 타임라인 표시(5절)가 **같은 데이터**를 본다
- 과거 날짜 전환(4절)이 안전해진다 — 전환한 날만 부채에 들어간다
- 새 스키마가 필요 없다 (`CarryOverSource.reason == .debtTransfer` + 상환 원장으로 충분)

## 3. 기능 1: 원장 기준 정리 — `reconciledDebt`를 전환일 집합 기반으로

### 현재

```
[startedAt−1, today) 범위의 모든 DailyBudget을 스캔
→ 임계값 이상 초과일의 초과액 합 − 갚은 금액
```

### 변경

```
converted = Σ (이 부채 기간에 남은 debtTransfer 크레딧 금액)
repaid    = Σ (상환 원장 금액)          ← 기존과 동일
remaining = max(0, converted − repaid)
```

- `debtTransfer` 크레딧 금액은 `reconcileDebtTransfer`가 과거 소비 수정 시 이미
  최신 초과액으로 유지한다. 즉 "크레딧 합 = 전환된 초과 합"이 항상 성립한다.
- 조회 범위: 활성 부채는 `startedAt` 이후의 크레딧. 완납 부채와 구간이 겹치지
  않도록 이전 부채의 `completedAt` 이후로 한정한다.
- **폴백 유지**: 전환 크레딧이 하나도 없는 부채(상환 계획 기능 이전 데이터)는
  지금처럼 재계산하지 않는다(`nil` 반환). "근거가 없으면 건드리지 않는다" 원칙 유지.

검증 기준: 기존 `DebtCarryOverDoubleCountTests` 전체가 결과 불변이어야 한다.
(같은 값을 다른 근거로 계산하는 리팩터링이다.)

## 4. 기능 2: 과거 날짜 초과 자동 전환

### 트리거

소비 CRUD(`createSpendingRecord`/`updateSpendingRecord`/`deleteSpendingRecord`)가
이미 부르고 있는 `recalculateCarryOverChain(from:)`의 전진 패스 안에서 전환한다.
재계산과 마찬가지로 **데이터 계층 책임**(2189500과 같은 원칙 — 호출자에게 맡기면 빠뜨린다).

> **구현 중 변경 (19bc3aa)**: 원안은 재계산 뒤 별도 패스(`convertPastOverspend`)로
> 돌리는 것이었으나, 그러면 크레딧이 붙는 순간 그 뒤 날들의 이월이 어긋난다
> (전환 크레딧은 그날 잔액을 올리므로 다음 날 이월이 달라진다). 한 번의 전진 패스
> 안에서 "이월 재계산 → 전환" 순으로 처리해야 체인이 맞는다.

### 규칙 (기존 전환 규칙을 과거 날짜에 그대로 적용)

변경일 다음날부터 오늘까지 각 날짜 X에 대해:

1. X에 이미 `debtTransfer` 크레딧이 있으면 건너뛴다
   (→ `reconcileDebtTransfer`가 체인 재계산 중에 이미 조정했다)
2. 전환액 = `convertibleOverspend(of: X−1 예산, deficit: X의 음수 일자이월)`
   — **그날 소비가 배정을 넘긴 만큼만**. 저축·투자·위시 저금이 만든 적자는
   전과 동일하게 부채가 되지 않는다
3. 임계값 = X의 기본 예산 × 10% (`DebtRepaymentPlan.threshold`, 기존 규칙 유지)
   — 미만이면 음수 이월로 남긴다
4. **급여일 컷오프**: X가 현재 급여 기간(`DailyBudgetCalculator.payPeriod`의
   `start`) 이전이면 전환하지 않는다. 이미 급여일 흡수로 정산됐거나 정산 판정을
   지난 기간의 초과를 뒤늦게 빚으로 만들지 않기 위함이다.
   급여 기간이 없는 모드(`lumpSum`/`fixedDaily`)는 컷오프 없음.
5. 전환 시: X에 `debtTransfer` 상쇄 크레딧 추가 + `addToDebt(amount:on: X)`.
   활성 부채가 없으면 새로 생성되며 이때 **`startedAt` = X (실제 전환일, 과거)**.
   `isPlanned = false`이므로 다음 홈 진입에서 기존 계획 확정 시트가 뜬다.

### 기존 코드와의 관계

- `processDailyBudgets`의 신규일 생성 경로(`overspendToConvert`)와 판정 기준이
  동일해야 한다 — 둘 다 `convertibleOverspend` + 하루 예산 10% 임계를 쓴다.
- `recalculateCarryOverChain` 문서 주석의 "재계산이 새 부채를 만들지는 않는다"는
  이 기능 도입으로 **의도적으로 폐기**된다. 멱등성은 유지된다: 두 번째 실행부터는
  크레딧이 이미 있으므로 `reconcileDebtTransfer` 경로로 들어가 같은 값으로 조정된다.

### 안내 (소급 입력 폭탄 대응)

여러 날이 한 번에 전환되면 부채가 갑자기 커진다. 전환 자체는 자동으로 두되:

- 새 부채가 과거 시작일로 생성된 경우, 계획 확정 시트(`DebtPlanSheet`) 상단 문구를
  "지난 {N}일 동안 {M}원 초과했어요"로 보강한다 (기존 `needsPlanPrompt` 흐름 재사용,
  새 팝업 없음)
- 이미 계획이 확정된 부채에 소급 합산된 경우는 기존처럼 조용히 잔액이 늘어난다
  (타임라인에 전환 이벤트로 남으므로 추적 가능)

- 하단: 완납 부채들 — 접힌 카드, 펼치면 동일 타임라인. "{시작일}부터 {완납일}까지

- 기존 `🎉 다 갚은 초과분` 카드(3f8af03)는 이 구조에 흡수된다
- "초과한 날" 탭(3개월 롤링)은 그대로 유지 — 부채와 무관한 소액 초과도 보여주는
  별개 관점이다

## 6. 기능 4a: "할부로 나누기" 선택지

`DebtPlanSheet`에 세 번째 선택지를 추가한다: **나눠 갚기(기존) / 할부로 나누기(신규)
/ 나중에(기존)**.

- 할부 선택 시: `InstallmentModel(title: "초과분 분할", totalAmount: 남은 부채,
  months: 사용자 선택, startYear/Month: 이번 달)` 생성 + 부채는 원장에 종결 기록 후
  완납 처리
- `DebtRepaymentSource`에 `.installment`("할부로 전환") 케이스 추가 — raw string
  저장이라 스키마 마이그레이션 불필요. 타임라인·갚은 내역에 출처로 표시
- 전환 후 하루 예산은 할부 월 납입액만큼 완만하게 줄어든다(기존 할부 계산 경로 재사용).
  부채 상환(하루 예산의 20%)보다 부담이 낮고 통계에도 남는다
- 여행처럼 "의도한 큰 지출"에 권하는 경로다. 시트 문구로 안내:
  "계획했던 큰 지출이라면 할부로 나누는 게 나아요"

## 7. 범위 밖 (별도 스펙 예정): 위시 지갑

계획된 여행은 위시 저금으로 모으는데, 정작 여행 중 소비를 기록하면 하루 예산에서
**또** 빠진다(이중 차감). 소비 기록을 위시 잔액에 연결하는 "위시에서 차감" 기능이
필요하다 — `SpendingRecord` ↔ `WishItem` 관계 추가(스키마 변경)가 필요한 유일한
항목이라 별도 설계로 분리한다. 이 문서의 4a(할부)가 먼저 들어가면 갑작스러운 여행은
당장 커버되므로 우선순위는 그 다음이다.

| 결정 | 선택 | 근거 |
|---|---|---|
| 전환 임계값 | 기존 10% 유지 | 소액 초과까지 빚으로 잡으면 관리 피로. "하루 사용금액보다 큰 소비"는 자연히 임계를 넘는다 |
| 원장 합산 근거 | 기간 스캔 → 전환일 집합 | 과거 전환과 공존 가능, 표시·계산 데이터 일원화 |
| 급여일 컷오프 | 현재 급여 기간 내 초과만 전환 | 흡수 정산과의 이중 부과 방지 |
| 새 부채 startedAt | 실제 전환일(과거 허용) | 타임라인이 정직해진다 |
| 소급 전환 안내 | 기존 계획 시트 문구 보강 | 새 팝업 추가 없이 기존 흐름 재사용 |
| 갚은 내역 탭 | 타임라인으로 개편(대체) | 같은 데이터의 더 나은 표현. 별도 섹션은 중복 |
| 자동 차감 원칙 | 유지 — 전환은 자동, 상환 시작은 계획 확정 후 | 기존 "자동 사용은 묻는다" 원칙과 일치 |

## 9. 테스트 계획

**원장 기준 정리** (`DebtCarryOverDoubleCountTests` 확장)
- 기존 전체 테스트 결과 불변 (리팩터링 검증)
- 전환 크레딧 없는 예전 부채 → `reconciledDebt() == nil` 유지
- 완납 후 새 부채 → 이전 부채 구간의 크레딧을 세지 않는다

**과거 날짜 자동 전환** (신규 `PastOverspendConversionTests`)
- 과거 날짜에 임계값 이상 소비 추가 → 부채 생성, `startedAt` = 전환일
- 활성 부채가 있으면 잔액 합산 (새 부채를 만들지 않는다)
- 임계값 미만 초과 → 전환 없음, 음수 이월 유지
- 저축·위시 저금이 만든 적자 → 전환 없음 (기존 원칙)
- 이전 급여 기간의 초과 → 전환 없음 (컷오프)
- 같은 날 반복 수정 → 크레딧은 `reconcileDebtTransfer` 경로로 조정, 이중 합산 없음
- 여러 날 한꺼번에 초과 입력 → 각 날짜별 전환, 합계 일치
- 삭제로 초과가 사라지면 → 크레딧·부채 감소 (기존 reconcile 동작 회귀 확인)

**타임라인**
- 이벤트 정렬·출처 라벨, 완납 부채의 소요일 계산
- 활성/완납/부채 없음 세 상태의 조회 결과

**할부 전환**
- 부채 완납 처리 + `.installment` 원장 + 할부 생성이 원자적으로
- 전환 후 `reconciledDebt` 잔액 0, 다음날 매일 상환 발생 없음

**날짜 의존성**: 기존 부채 테스트들이 25일(급여일)에 깨지는 문제가 확인돼 있다.
이 스펙의 신규 테스트는 `payday`를 실행일과 겹치지 않게 동적으로 잡는다
(예: 오늘 기준 ±15일). 기존 테스트 정리는 별도 작업.
