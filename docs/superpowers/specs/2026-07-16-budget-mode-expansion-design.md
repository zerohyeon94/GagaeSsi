## 1. 배경·목적

현재 앱은 "월급을 받는 사용자"를 전제로 한다. 그러나 다음 사용자·상황을 수용하지 못한다:

1. **정기 용돈을 받는 학생** — 월급은 아니지만 구조는 동일 (금액 + 주기 + 받는 날)
2. **수입이 없는 취준생 등** — 모아둔 돈으로 일정 기간을 버티는 멘탈 모델
3. **수입 중단·전환기** — 퇴사·휴직으로 급여가 끊긴 경우
4. **설치일 ~ 첫 급여일 갭** — 예: 5일 설치 + 급여일 10일이면 현재 구현은 "지난달 급여 기간"으로 간주해 정상 일일 예산을 그대로 보여줌. 실제로는 월급 전 며칠은 돈이 부족한 경우가 많아 현실과 어긋남.

핵심 통찰: 기존 엔진은 이미 **"(금액, 기간) → 기본 일일 예산 + 이월"** 구조다. 월급은 금액의 출처일 뿐이므로, 기본 일일 예산의 산출 방식만 모드화하면 이월·저금(위시리스트)·통계는 변경 없이 동작한다.

## 2. 예산 모드 3종

### 2-1. 정기 수입 모드 (기존 모델의 일반화)

- 입력: 수입 금액 + 주기(**매월/매주**) + 받는 날 (매월: 1~31일, 매주: 요일)
- 계산: `(수입 − 고정비) ÷ 주기 일수` — 기존 로직과 동일, 주기만 일반화
- 용어 변경: 온보딩·설정에서 "월급" → "수입"으로 라벨 일반화
- 기존 사용자는 자동으로 이 모드(매월)로 마이그레이션

### 2-2. 총액 관리 모드

- 입력: 총액(지금 가진 돈) + 종료일(언제까지 버틸지)
- 계산: `총액 ÷ (시작일~종료일 일수)` — 기간 내 균등 배분, 이월 규칙 동일 적용
- 급여일 개념 없음. 기간이 고정되어 있다는 점만 다름
- 종료일 도달 시: 홈에 "기간이 끝났어요 — 예산을 다시 설정해주세요" 안내 → 재설정 유도
- 중도에 돈이 생기면(수입 발생): 총액·종료일 수정 → 오늘부터의 기본 예산만 재계산 (기존 "설정 변경 시 재계산" 규칙과 동일)

### 2-3. 하루 예산 직접 설정 모드

- 입력: 하루 금액 하나
- 계산: 기본 일일 예산 = 입력값 (산출 없음)
- 수입 구조를 묻지 않는 최소 폴백. 이월·저금·통계는 동일하게 동작

## 3. 온보딩·설정 변경

### 3-1. 온보딩 흐름

1. 첫 화면: "예산을 어떤 방식으로 관리할까요?" — 카드 3개 (정기 수입 / 모아둔 돈으로 생활 / 하루 예산 직접 설정)
2. 모드별 입력 화면 1~2개 (기존 SetupSalaryView·SetupFixedCostView는 정기 수입 모드 전용으로 재배치)

### 3-2. 첫 급여일 갭 처리 (정기 수입 모드 한정)

- 설정 완료 시점이 받는 날 이전이면 한 가지를 추가로 묻는다: **"다음 받는 날까지 쓸 수 있는 돈이 지금 얼마나 있나요?"**
- 부분 기간(오늘 ~ 받는 날 전날)의 기본 예산 = `남은 돈 ÷ 부분 기간 일수` — 총액 모드 계산기를 그대로 재사용
- 받는 날부터 정상 사이클 진입. 부분 기간 마지막 날 잔액은 기존 규칙대로 이월

### 3-3. 모드 전환 (설정)

- 설정에서 언제든 모드 전환 가능 (수입 중단 시 총액 모드로 전환하는 것이 공식 해법)
- 전환 시 기존 규칙 적용: **오늘의 기본 예산만 재계산**, 과거 기록·이월·소비는 보존
- 활성 위시 저금이 있으면 그대로 유지 (저금은 모드와 무관)

## 4. 데이터 모델·엔진 변경

### 4-1. CoreData (lightweight migration)

`BudgetConfig`에 필드 추가:

| 필드 | 타입 | 용도 |
|---|---|---|
| `mode` | String | `recurring` / `lumpSum` / `fixedDaily` (기존 데이터 기본값 `recurring`) |
| `cycle` | String? | 정기 수입: `monthly` / `weekly` |
| `totalAmount` | Int? | 총액 모드: 총액 |
| `periodStart` / `periodEnd` | Date? | 총액 모드 기간, 갭 처리 부분 기간 |
| `dailyAmount` | Int? | 직접 설정 모드 |

기존 `salary`·`payday`·`fixedCosts`는 정기 수입 모드 전용으로 유지.

### 4-2. 계산 엔진

- `DailyBudgetCalculator.calculate(from:for:)`가 `mode`에 따라 분기해 **기본 일일 예산만** 산출
- `processDailyBudgets(upTo:)` 이월 체인, 위시 저금 차감, 통계는 변경 없음

## 5. 엣지 케이스

| 케이스 | 처리 |
|---|---|
| 총액 모드 종료일 경과 | 마지막 날 예산으로 유지하지 않고, 재설정 안내 표시 (기본 예산 0 취급 여부는 구현 시 결정) |
| 총액 < 고정 지출 성격의 큰 지출 예정 | 총액 모드에는 고정비 개념 없음 — 월세 등은 총액에서 미리 빼고 입력하도록 안내 문구 |
| 매주 주기 + 고정비 | v1에서는 주 주기 선택 시 고정비 입력 숨김 (제안) — 월 고정비의 주 단위 배분은 복잡도 대비 효용 낮음 |
| 갭 처리 중 설정 변경 | 부분 기간도 "오늘만 재계산" 규칙 동일 적용 |
| 급여일 말일 보정 (기존 P0 이슈) | 정기 수입(매월) 모드에 동일 적용 — 본 기획과 함께 처리 권장 |

## 6. 결정 필요 사항

1. **버전 순서**: 위시리스트 저금(v1.2 후보)과 예산 모드 확장 중 무엇을 먼저 갈지. 예산 모드가 신규 사용자층(학생·취준생)을 여는 기반 기능이므로 순서 교체 검토 가치 있음.
2. **매주 주기 지원 범위**: v1에 포함할지, 매월만 먼저 출시할지.
3. **총액 모드 종료일 경과 시 기본 예산**: 0으로 둘지, 마지막 값 유지할지.

## 7. 범위 제외 (v2+)

- 일회성 급여 지연 처리 ("이번 급여 건너뛰기 → 기간 연장")
- 복수 수입원 (월급 + 부수입 동시)
- 프리랜서형 불규칙 수입 자동 평활화
